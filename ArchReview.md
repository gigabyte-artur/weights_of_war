# Архитектурный обзор Weights of War

> Дата: 16.10.2026
> Объект: `core/src/main/java/ru/gigabyteartur/weights_of_war` (libGDX, Java 11, Gradle 9.7.1)
> Подход к анализу: модульная декомпозиция в духе Udi Dahan / Particular Software — автономные бизнес-возможности, границы сервисов и владение данными, Composite UI.

## Прочитанные классы

`Main`, `GameWorld` (1480 строк), `PlacedObject`, `BattleObject`, `Fraction`, `FogOfWar`, `BattleUnitCommon` (857 строк), `BattleBuildingCommon`, `BuildingCore` (~450 строк), `CommandPanel`, `MiniMap`, `CommandUnit`, `CommandThink`, `CommandAttackTarget`, `SensorCommon`/`SensorEnemyUp`, `NeuroNet` (635 строк), `Evolution`, `HeadlessGame`.

---

## Вводная оценка

Формально проект разбит на пакеты (`units`, `buildings`, `commands`, `Sensors`, `neuro_net`, `evo`) — но это **технические слои, а не бизнес-возможности**. Фактическая архитектура — **один мутабельный граф объектов вокруг монолитного `GameWorld`**, по которому все модули ходят напрямую и мутируют состояние друг друга. Автономных capabilities в смысле Dahan здесь нет.

---

## 1. Модульная декомпозиция

### 1.1. `GameWorld` — god-object, он же «shared everything»

`GameWorld` (1480 строк) одновременно является:

| Ответственность | Методы |
|---|---|
| контейнер состояния симуляции | `units`, `gameOver`, `winnerFraction`, `gameSpeed`, границы мира |
| пространственные запросы (инфраструктура) | `FindNearestEnemy`, `FindNearestEnemyUp/Right/Down/Left`, `FindNearestEnemyBuilding`, `FindOwnCore`, `FindNearestAlly*`, `FindNearestWoundedAlly*`, `CountEnemies*`, `CountAllies*`, `FindMostWoundedAlly`, `CountHealersOn`, `IsAreaOccupied*`, `FindFreePosition` |
| жизненный цикл партии (orchestration) | `Update`, `CheckGameOver`, `IsOnlyOneFractionLeft`, `IsSecondGenerationReached`, `GetMaxGeneration`, `FindWinnerFraction`, `FindWinnerByFitness` |
| запросы фитнеса/эволюции | `GetTopAliveUnits`, `GetBestAliveUnit`, `GetBestEnemyUnit`, `GetEffectiveFit`, `CheckUnitsStagnation` |
| персистентность | `SavesDirectory`, `LoadSavedNeuroNets`, `LoadNetIfExists`, `SaveBestNetworks`, `SaveBestNetwork` |
| логирование нейросети | `CleanupNeuroLogs`, `BuildNeuroLogFileName`, `GetSensorNames`, `PickRandomUnit` |
| глобальное состояние | `static debugMode` + `getDebugMode`/`setDebugMode` |

Каждый объект получает `GameWorld` параметром и вызывает его напрямую: команды (`CommandAttackTarget.Execute(unit, world)`), сенсоры (`SensorEnemyUp.CheckSensor(Object_in, world)`), юниты (`BattleUnitCommon.Update(world)`), здания (`BuildingCore.Update(world)`), UI (`CommandPanel.ShowUnitInfo(..., world)`).

**Что нарушено.** По Dahan граница сервиса = владение данными + контракт. Здесь один объект владеет *всем* и является контрактом для всех. Нет ни одного автономного модуля, который владел бы своим состоянием и своими правилами — вместо этого все «знают» `GameWorld` и тянут из него данные.

**Последствия.** Любое изменение пространственного представления (ввести spatial hash вместо линейного скана `for (PlacedObject unit : units)`), любое изменение семантики тумана войны или фитнеса заставляет трогать один класс на 1480 строк и, фактически, пересобирать ментальную модель всего проекта. Модули нельзя развивать независимо: они сцеплены через этот общий объект.

**Направление.** Разделить `GameWorld` на несколько владельцев данных с явными контрактами: `WorldState` (только коллекция объектов + границы), `SpatialIndex`/`VisionQueries` (пространственные запросы как отдельная capability, скрывающая структуру хранения), `MatchLifecycle` (правила победы/поколений), `FitnessRegistry` (фитнес). `GameWorld` остаётся тонкой композицией-фасадом, а не складом всех методов.

### 1.2. Одна бизнес-ответственность размазана по нескольким модулям — «зрение/таргетинг»

Правило «кто есть враг/союзник в пределах обзора» выражено в ~15 местах с копипастой:

- `BattleObject.FindSightCandidate` (на сущности),
- `GameWorld.FindCandidate` / `FindAllyCandidate` / `FindWoundedAllyCandidate`,
- `GameWorld.FindNearestEnemy` / `FindNearestEnemyBuilding`,
- 4 метода `FindNearestEnemyUp/Right/Down/Left` (каждый — идентичный цикл ~20 строк с единственным отличием в сравнении координат),
- 8 методов `CountEnemies*/CountAllies*`,
- 4 метода `FindNearestWoundedAlly*`.

Это **одна бизнес-возможность** («что видит юнит») с десятком дублирующихся реализаций, а не с одним владельцем.

26 классов-сенсоров (`SensorEnemyUp`, `SensorCountAllyRight`, …) — механическое зеркало этой API-поверхности: каждый сенсор — обёртка над одним методом `GameWorld`. То есть пакет `Sensors` — не capability, а фасад над god-object.

**Последствия.** Изменение правила видимости требует правок в десятке методов, и легко рассинхронизировать. Добавление нового сенсора = новый метод `GameWorld` + новый класс + правка `CreateBaseSensors` + правка размера входного слоя сети.

**Направление.** Выделить `VisibilityQuery`/`SpatialQuery` как единый компонент с методами «ближайший враг в направлении», «счётчик союзников в радиусе» и т.д., а сенсоры сделать чистыми читателями этого компонента (а не каждый — отдельным запросом к миру).

### 1.3. Понятие «тип юнита» не смоделировано — захардкожено в 6+ местах

Добавление нового типа юнита сегодня требует правок как минимум в:

1. `BuildingCore.ProduceUnits` — новый блок из ~25 строк + константа счётчика (весь метод — 5 одинаковых блоков копипасты),
2. `GameWorld.SaveBestNetworks` / `SaveBestNetwork` (хардкод списка классов),
3. `GameWorld.LoadSavedNeuroNets` (хардкод списка файлов),
4. `CommandPanel.ShowCoreInfo` (хардкод строк «Мечник/Лучник/…»),
5. `HeadlessGame.create` (хардкод списка заглушек текстур),
6. `BattleUnitCommon.CreateNeuroNetUnit` / топология сети.

Плюс `BuildingCore` держит **10 параллельных `ArrayList`** (`NetSwordmen`/`NetSwordmenFits`/`NetArchers`/…) — классический «parallel arrays / type switch» антипаттерн.

**Что нарушено.** Бизнес-возможность «производство и эволюция юнитов» жёстко параметризована конкретными классами, а не данными/конфигурацией. Каждый новый тип ломает N файлов — ровно та связность, которую Dahan называет отсутствием автономности.

**Направление.** Ввести явную модель «тип юнита» (фабрика + конфигурация: счётчик, класс, имя файла, пул чемпионов), чтобы `ProduceUnits` был одним обобщённым циклом по списку типов, а не 5 блоками.

## 2. UI и границы модулей

### 2.1. Архитектура сформирована вокруг одного экрана боя

Вся игра — один экран, один мир, один цикл `render()`. `Main` (композиция корня) сам делает: `world.Init/Update/Show`, выделение, приказы, клик по миникарте, камеру, кнопку отладки, кнопку выхода, создание шрифта, отрисовку фона травы, текст победителя. Это не композиция независимых capabilities, а монолит `ApplicationAdapter`.

«То, что данные отображаются на одном экране, не означает, что ими должен владеть один модуль»: в Weights of War экран боя породил **единый мир-модель**, и всё остальное построено поверх него.

### 2.2. Доменная сущность = рендер + UI-выделение + состояние

`BattleObject` импортирует графику libGDX (`Texture`, `SpriteBatch`, `Pixmap`, `Color`) и **рисует сам себя**:

```java
public void Show(SpriteBatch batch) {
    batch.draw(mainTexture, getX(), getY(), getWidth(), getHeight());
    DrawFactionCircle(batch);
    DrawHealthBar(batch);
    if (selected) DrawSelectionFrame(batch);
}
```

Флаг `selected` — доменное поле, но по смыслу это UI-состояние выделения. Поля `static whitePixel`/`whiteCircle` — глобальные графические ресурсы на доменном классе.

**Что нарушено.** Домен и презентация слиты на уровне сущности. Чистая симуляция неотделима от графики.

**Доказательство — `HeadlessGame`.** Чтобы прогнать «чистую» ИИ-эволюцию без окна, пришлось подменять `Gdx.gl` и `Gdx.graphics` через `java.lang.reflect.Proxy` (`noOpGL20()`, `fixedGraphics()`) и вручную класть заглушки текстур в `TextureCache`. Это дымящийся ствол: симуляция *настолько* переплетена с рендером, что её нельзя запустить без мока графического слоя.

**Последствия.** Невозможно эволюционно обучать/тестировать ядро симуляции в изоляции; `HeadlessGame` — это второй `ApplicationAdapter`, **дублирующий** оркестрацию партии (`StartNewGame`/`FinishGame`/цикл `render`) поверх `Main`. Два entry-point, два сценария жизненного цикла — расхождение неизбежно.

**Направление.** Разделить на «симуляцию» (чистые доменные объекты без libGDX) и «рендер-адаптеры» (отдельные View-объекты, читающие состояние). Тогда headless-режим — это просто другой драйвер симуляции, а не мок графики. UI (`Main`, `CommandPanel`, `MiniMap`) должен получать **read-model**/снимки состояния, а не обходить мутабельный граф.

### 2.3. UI пересчитывает доменную логику на лету

`CommandPanel.ShowUnitStats` в цикле отрисовки заново создаёт сенсоры и вызывает их:

```java
ArrayList<SensorCommon> sensors = unit.CreateSensors();
for (int i = 0; i < sensors.size(); i++) {
    int value = sensor.CheckSensor(unit, world);   // полный пересчёт на каждый кадр
    ...
}
```

и тянет `world.CountAllies(unit, ...)`, `world.CountEnemies(unit, ...)`. То есть **UI повторно исполняет доменную логику** (сенсоры) и ходит в глубь мира ради отображения. Это не Composite UI по Dahan (композиция read-моделей), а прямое чтение мутабельной доменной модели из представления.

**Последствия.** Любое изменение сигнатуры сенсора/запроса ломает UI; UI знает о внутренностях домена больше, чем нужно; производительность рендера завязана на O(N) сканы по всем юнитам.

**Направление.** UI читает только готовые данные (снимок «инфо о выделенном»), которые симуляция формирует отдельно, а не дергает сенсоры/запросы в кадре.

## 3. Архитектура внутри модулей

### 3.1. `BuildingCore` — перегруженный агрегат: производство + эволюция + память чемпионов

`ProduceUnits` (~200 строк) смешивает: таймер производства, проверку разрушенной башни, инкремент поколения, создание сетей первого поколения, проверку стагнации, и для каждого из 5 типов — отбор топ-юнитов, горизонтальный перенос генов врага, генерацию потомства, обновление пула чемпионов, спавн и реюз мёртвых объектов. Это orchestration + доменная логика + персистентность в одном методе, с 5× дублированием.

**Что нарушено.** У модуля нет единой ответственности: он и «фабрика юнитов», и «оркестратор эволюции», и «хранилище чемпионов». Причём чемпионские пулы (10 `ArrayList`) — это состояние *эволюционной* возможности, зашитое в здание.

**Направление.** Выделить `GenerationOrchestrator`/`PopulationManager` как отдельную capability, которой `BuildingCore` отдаёт команду «произвести поколение», не зная деталей отбора/кроссинговера/пулов.

### 3.2. Возможность «эволюция/фитнес» размазана по 5 классам

Фитнес и эволюция не имеют единого владельца:

- **`BattleUnitCommon`** хранит `fit`, `lastFit`, `staleWaves`, `FitType` и `CheckStagnation`;
- **`CommandAttackTarget`** начисляет фитнес прямо в боевой команде (`unit.IncreaseFit(damageToApply, ...)`, `IncreaseFit(KILL_FIT_BONUS, KILLED_ENEMY_UNIT)`, `IncreaseFit(blockedToApply, BLOCKED_ENEMY_DAMAGE)`);
- **`BuildingCore`** запускает стагнацию и владеет пулами чемпионов;
- **`GameWorld`** делает отбор (`GetTopAliveUnits`, `GetBestAliveUnit`, `GetEffectiveFit`);
- **`Evolution`** делает кроссинговер/мутацию/элитизм.

Правило «за что и сколько даётся фитнес» вшито в команды боя, а не в эволюционный модуль. Изменение фитнес-семантики требует правок в 4+ файлах.

**Направление.** Свести правила фитнеса в один компонент (`FitnessPolicy`), а боевые команды — лишь *сообщать о событиях* («нанесён урон», «убит враг»), по которым фитнес начисляется централизованно.

### 3.3. `neuro_net` — доменный объект, переплетённый с персистентностью и глобальным логированием

`NeuroNet` сам делает XML-сериализацию (~200 строк `SaveToFile`/`LoadFromFile`), хранит версию формата `NEURO_NET_FORMAT_VERSION`, и содержит **глобальное мутабельное состояние логирования**:

```java
private static NeuroNet logTarget;
private static String logFileName;
private static String logUnitName;
...
public void CalcSignals() {
    ...
    if (this == logTarget && logFileName != null) {
        SaveToFile(logFileName, logUnitName, logInputNames, logOutputNames);
        ...
    }
}
```

Логирование встроено в **горячий путь вычислений** через статический сайд-канал, а не как отдельный наблюдатель/событие.

**Что нарушено.** Нейросеть не является чистым value-объектом: у неё есть скрытое глобальное состояние, I/O-зависимость и забота о формате файла. Это инфраструктурная ответственность, смешанная с доменной.

**Последствия.** Сеть нельзя эволюционировать/клонировать в изоляции без XML и глобального состояния; логирование не масштабируется (один глобальный `logTarget` на процесс), а сериализация и формат-версия завязаны на домен.

**Направление.** Вынести сериализацию в отдельный `NeuroNetSerializer` (инфраструктура), а логирование — в подписчика на событие «сеть рассчитана», без статического состояния в `NeuroNet`.

### 3.4. Контракт «сенсоры ↔ сеть ↔ команды» неявен и держится на магических числах

Размер входа сети захардкожен как `26` в `BattleUnitCommon.CreateNeuroNetUnit()`, при этом `CommandThink.CreateBaseSensors()` добавляет ровно 26 сенсоров, а согласование происходит через `Math.min(sensors.size(), inputLayer.size())`. Выход `10` нейронов ↔ `switch (index)` в `CreateCommand` ↔ `GetCommandNames()` (список 0..10) — три копии одной таблицы соответствий, синхронизируемые вручную.

**Что нарушено.** Скрытый контракт между модулями (`neuro_net` и `commands`/`Sensors`) держится на совпадении чисел и порядка, без единого источника истины. Это источник хрупких багов («закомментирован `case 8`» — и появляется `EXCLUDED_NEURON_INDEX = 8` как заплатка).

**Направление.** Единое описание «входы = сенсоры, выходы = команды» как данные (список команд/сенсоров), из которого *порождаются* и топология сети, и таблица соответствий, и имена для логов.

## 4. Наиболее серьёзные архитектурные проблемы (по важности)

### 1. `GameWorld` как монолитный god-object / «shared everything» (нет сервисных границ)

- **Пример:** 1480 строк, смесь состояния, ~30 пространственных запросов, оркестрация партии, запросы фитнеса, персистентность, логирование; каждый объект (`BattleUnitCommon`, `BuildingCore`, `CommandAttackTarget`, каждый `Sensor*`, `CommandPanel`) получает `GameWorld` и тянет/мутирует его напрямую.
- **Нарушение:** отсутствие автономных capability и границ владения данными — все модули «знают» один общий объект вместо обмена через контракты.
- **Последствия:** нулевая независимая развиваемость; любое изменение представления данных, правил видимости или фитнеса трогает центральный класс и всех его потребителей; тесты вынуждены собирать целый `GameWorld`.
- **Исправление:** декомпозировать на владельцев данных (`WorldState`, `SpatialIndex`, `MatchLifecycle`, `FitnessRegistry`), оставив `GameWorld` тонким фасадом-композицией.

### 2. Один мутабельный граф объектов, где модули напрямую мутируют друг друга; домен слит с презентацией

- **Пример:** `CommandAttackTarget` делает `target.setHealth(...)`, `((BattleUnitCommon) target).MarkAttacked()`, `IncreaseFit(...)` — кросс-мутация чужого состояния без границы; `BattleObject` рисует себя (`Show(SpriteBatch)`) и держит UI-флаг `selected`; `Main`/`CommandPanel` обходят мутабельный мир в кадре.
- **Нарушение:** не автономные сервисы, а общий граф без границ; модель сформирована экраном боя (а не бизнес-возможностями); нет read-model для UI.
- **Последствия:** симуляцию нельзя отделить от графики (доказательство — мок `GL20`/`Graphics` через `Proxy` в `HeadlessGame`); UI знает внутренности домена; сущности перегружены.
- **Исправление:** отделить чистую доменную симуляцию от рендер-адаптеров и от UI read-моделей; взаимодействие между модулями — через события/команды, а не прямую мутацию.

### 3. Возможность «эволюция/фитнес» размазана по 5 классам; «тип юнита» захардкожен в 6+ местах

- **Пример:** фитнес начисляется в `CommandAttackTarget`, стагнация в `BattleUnitCommon`, отбор в `GameWorld`, кроссинговер в `Evolution`, пулы чемпионов в `BuildingCore` (10 параллельных `ArrayList`); `ProduceUnits` — 5 идентичных блоков, а список типов повторён в `GameWorld`, `CommandPanel`, `HeadlessGame`, `BuildingCore`.
- **Нарушение:** одна бизнес-возможность без владельца; параллельные массивы и type-switch вместо модели «тип юнита».
- **Последствия:** добавление типа юнита = правки в ~6 файлах; изменение фитнес-семантики = правки в 4+ файлах; высокая связанность.
- **Исправление:** ввести `FitnessPolicy` (боевые команды лишь сообщают события), обобщённый `PopulationManager`/`GenerationOrchestrator`, и конфигурацию типов юнитов как данные.

### 4. Неявный контракт «сенсоры ↔ сеть ↔ команды» на магических числах + копипаста правил видимости

- **Пример:** `26` входных нейронов в `CreateNeuroNetUnit` ↔ 26 сенсоров в `CreateBaseSensors`; `10` выходов ↔ `switch` в `CreateCommand` ↔ `GetCommandNames`; правило «враг/союзник в обзоре» продублировано в ~15 методах `GameWorld` + `BattleObject.FindSightCandidate`, а 26 сенсоров — обёртки над этими методами.
- **Нарушение:** нет единого источника истины для «что видит/что может делать ИИ»; контракт держится на совпадении чисел и порядке.
- **Последствия:** добавление сенсора/команды — кросс-слойное изменение; рассинхронизация топологии сети и сенсоров — типовой баг; дублирование правила видимости неизбежно расходится.
- **Исправление:** описать входы/выходы как данные, из которых порождаются топология сети и таблица команд; выделить единый `SpatialQuery`/`VisibilityQuery`.

### 5. `NeuroNet` — доменный объект, переплетённый с I/O и глобальным логированием

- **Пример:** `SaveToFile`/`LoadFromFile` (~200 строк XML) внутри `NeuroNet`; `static logTarget`/`logFileName` и вызов `SaveToFile` внутри `CalcSignals`.
- **Нарушение:** инфраструктурная ответственность (сериализация, формат-версия, логирование) внутри доменного вычислительного объекта; скрытое глобальное состояние.
- **Последствия:** сеть нельзя использовать как чистый value-объект; логирование не масштабируется (один глобальный target); формат и логика связаны.
- **Исправление:** вынести `NeuroNetSerializer` (инфраструктура) и логирование в подписчика на событие, убрав статику из `NeuroNet`.

## Резюме

Ключевой дефект — не отсутствие пакетов, а отсутствие **автономных бизнес-возможностей с границами владения данными**. Вместо этого: один god-object `GameWorld`, один мутабельный граф, по которому все ходят и мутируют друг друга, домен слитый с рендером и UI, и возможности (эволюция, зрение, персистентность), размазанные по классам и держащиеся на дублировании и магических числах. Это ровно те антипаттерны, против которых направлен подход Dahan / Particular Software.
